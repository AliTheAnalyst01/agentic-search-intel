Agentic Search Intelligence

technical assessment / Syed Faizan

Five agents, each doing exactly one job, answering how a brand shows up in Google results and inside AI assistants.

Built with LangGraph and FastAPI over DataForSEO's search and AI-visibility APIs. Everything below is output from real runs, not illustration. This page is a walkthrough; the code is on GitHub.

Three of the five nodes are hairlines because they finish in under three milliseconds combined. The two model calls account for 99.98% of the run. Knowing that is the difference between optimising the right thing and rewriting a parser that was never slow.

The question it answers

Ask it in plain language. It plans the lookups, makes them, reads the responses, reasons over the numbers, and writes up what it found.

Marketing teams can see their Google rankings. What they cannot see is whether ChatGPT names them when someone asks for the best tool in their category — and increasingly that is where the buying research starts. Answering it by hand means opening a dozen tabs, asking four assistants the same question, and typing numbers into a spreadsheet that is stale tomorrow.

Five agents, one job each

No agent both fetches data and reasons about it. That separation is the point: when something breaks, exactly one agent is responsible for it.

query_planner Decides which lookups would answer the question fetches anything
retrieval Makes the calls, hands back the raw responses untouched parses or reshapes
extraction Turns three different response shapes into one clean schema calls an API, or interprets
analysis Reasons over the normalised rows to produce findings retrieves, parses, or assigns a score
report Assembles the structured output and the written summary reasons, or invents a finding
fallback Records why a run degraded, when an earlier stage produced nothing usable produces findings

The separation is tested rather than asserted. Each node returns only the state keys it owns, and a test fails if that changes — test_planner_does_not_fetch_anything, test_response_is_returned_unmodified, test_node_does_not_normalize.

What it produces

A JSON report for machines and a written summary for people. Below is the summary from a real run, unedited.

Search and AI visibility review for Surfer SEO (surferseo.com). Queries analysed: 4. Visible: 2. Not visible: 0. Could not be checked: 2. Highest-opportunity queries: - surfer seo alternative (opportunity 0.574, 590 searches/mo, difficulty 28, not checked) - seo content optimization (opportunity 0.557, 2400 searches/mo, difficulty 52, not checked) - What are the best SEO tools? (opportunity 0.49, n/a searches/mo, difficulty n/a, visible in AI answers) - best seo tool (opportunity 0.339, 8100 searches/mo, difficulty 74, #3) Queries marked "not checked" have provisional scores: no SERP lookup covered them, so their visibility is unverified. Recommended content: - [medium] Surfer SEO Alternatives: How We Compare (comparison_page) Captures users searching for alternatives — 590 monthly searches.

Read the fourth column. Two queries say not checked, not "not ranking" — and the AI-visibility query reports n/a search volume rather than zero, because a conversational prompt has no search volume to measure.

Three states, not two

The distinction that took a bug to get right, and the one I would defend hardest in a review.

visible

We looked, and the brand is there. A position is recorded.

not_visible

We looked, and the brand is absent. That is a finding.

unknown

We never looked, or the lookup failed. That is not a finding.

Collapsing the third state into the second reports "you are not ranking" when the truth is "we could not check" — confident, wrong, and pointing the customer in the wrong direction. An early version did exactly that, passed every test, and produced a report whose own two lines contradicted each other. The model then faithfully described the contradiction it had been handed.

When things break

The interesting question is never whether an external API fails. It is what the customer sees when it does. Three scenarios, each real output.

A transient failure the caller never notices

Two rate-limit responses on the same call, then success. Exponential backoff with full jitter, so many clients do not all retry in the same instant and knock over a service that has just recovered.

retrieval status : ok attempts on SERP : [3, 1, 1, 1, 1] retries recorded : 2

A failure that is not worth retrying

A 401 means the credentials are wrong. Retrying it three times achieves nothing and burns the rate limit, so retryability is a property of the error type rather than a decision made at each call site.

SERP calls made : 2 (2 planned calls, 1 attempt each) retrieval status : partial error recorded : AuthError: 401 Unauthorized

Everything fails, and a report still arrives

When no call succeeds there is nothing to extract or analyse, so the graph routes around both of those agents to a fallback that records why. A partial run returns an explained gap, never an empty response and never a crash.

nodes visited : query_planner → retrieval → fallback → report overall status : partial degradation : Every retrieval call failed, so there was no data to analyse.

The trap in the upstream API

DataForSEO returns HTTP 200 for almost everything. The real outcome hides in the response body, on two separate levels.

layer 1
HTTP status

Only 401, 402, 404 and 500 ever appear here. Everything else is a 200.

layer 2
body status_code

Success is 20000–29999. A validation failure arrives as a 200 carrying 40501.

layer 3
per-task status_code

The call can be accepted while the task inside it still failed to produce data.

A client built on HTTP codes alone treats those failures as successes and passes empty payloads downstream, where they surface three agents later as "no results found" instead of "authentication is broken". Task codes do not even split cleanly by range: 40501 is our own malformed request and must not be retried, while 40101 is an upstream search engine failing after their internal retries, which should be.

How a query gets scored

The formula was mine to define. Three weighted components, and the model never touches any of them.

0.40Gap Heaviest weight. A query you already rank first for is not an opportunity, however large it is.
0.35Volume Log-scaled, because 100 to 1,000 searches matters far more than 10,000 to 11,000.
0.25Ease The inverse of keyword difficulty.
not visible1.00
position 11+0.60
position 4–100.30
position 1–30.00
never checked0.50

Neutral, not 1.00. Scoring a failed lookup as wide-open lets a broken call manufacture a top priority out of nothing. Unmeasured search volume and difficulty are treated the same way.

The model writes the prose — the finding titles, the rationales, the suggested content angles. Every number is computed in code, and priority is derived from the score by threshold. Letting the model assign priority would create a second source of truth that visibly contradicts the score printed next to it.

What is in the repository

It clones and runs with no credentials and no network: the DataForSEO layer ships with a mock client that can be scripted to fail on demand.

LangGraph for the DAG, FastAPI and SQLAlchemy for the API and persistence, Pydantic for the tool schemas and argument validation, structlog for the JSON logs and correlation IDs, httpx for the transport. Six REST endpoints, including one that re-runs a single query by entering the graph part-way through and skipping the planner entirely.
